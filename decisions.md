# Decisions

The reasoning behind choices that aren't obvious from reading the code. Ordered roughly by how likely they are to matter to a future session.

---

## No build tooling — forced by the environment, not a preference

The dev machine has no Node, no npm, no Python, no ImageMagick, no ffmpeg (all confirmed by direct probing at project start). A React/Vite scaffold was the initial instinct but had to be abandoned once `node -v` came back "command not found." The fallback — plain HTML/CSS/vanilla JS with classic (non-module) `<script>` tags, Tailwind via CDN — was chosen specifically because:
- Classic scripts (not `type="module"`) work over `file://` without CORS errors, so the site can be opened by double-clicking `index.html` with zero server.
- No install step means the user (who also doesn't have Node) can always run it.

**If a future session finds Node/npm available**, that doesn't mean migrate to a build — check with the user first, since the whole file structure and the "just open index.html" promise depends on staying build-free.

## Why a local server exists at all, given `file://` works

Claude's own sandboxed Browser-pane preview tool renders local `file://` pages as an isolated one-shot snapshot (loaded as an internal `data:` URL) that cannot fetch sibling relative files — CSS, JS, and images all silently fail to load in *that specific tool*, even though the same file opened in a real browser works fine. This was discovered early and is a limitation of the preview tool, not of the site. `scripts/serve.ps1` (a hand-rolled `System.Net.HttpListener` static file server, since no other option existed) exists so Claude sessions can visually verify the site through the Browser pane. The user's own browser never needed this — but using it consistently avoids re-discovering this quirk.

## The logo: two rounds

Round 1: the user shared a logo image inline in chat. Claude could *see* it (vision) but had no filesystem path to it — chat-pasted images aren't written to any location Read/Bash can reach. Claude reconstructed an approximation in SVG (a hand-drawn-style crown + distressed-filter wordmark). This was explicitly **not** a copy of the real asset.

Round 2: the user saved the actual file to `C:\Users\shaba\Downloads\...` and gave the path, which Claude *could* read. That file was cropped (via PowerShell `System.Drawing`, the only image-editing capability available) into three assets: `crown-mark.png`, `wordmark-mark.png`, `fanwarsindia-logo.png` (full lockup). Backgrounds were made transparent via a hand-written chroma-key script (`scripts/make-transparent.ps1`) since there's no image editor available. The SVG reconstruction was deleted once the real asset existed.

**Bug caught mid-project**: the header/fan-card initially placed the crown *beside* the wordmark (horizontal layout) instead of *above* it (the actual logo's real composition). The user had to point this out explicitly ("crown is not on top... I cannot tell you such small things, you need to check all these") — a fair criticism. Fixed by stacking crown-above-wordmark everywhere, and by using the single pre-composed `fanwarsindia-logo.png` in the hero/footer (where the whole point is an exact, large reproduction) rather than reassembling pieces.

## One crown everywhere; one naming format everywhere (2026-09-19)

The user pointed out the crown wasn't consistent across the site. Cause: the #1 rank badge and Legend badge used `Icons.crown`, a hand-drawn generic outline SVG, next to a logo whose crown is a rough brush-painted red one. Fix was to delete the generic crown entirely and route every crown through the logo's actual `crown-mark.png` (`brandCrownHTML()`), rather than tweaking the SVG to look "closer" — a look-alike would drift again. Legend's crown is therefore red (the logo's colour), not gold; `FAN_LEVELS.legend.color` is now only used by the canvas fan-card dot.

Same principle for naming: buttons said "Support Pawan" while the success screen said "You just backed PAWAN KALYAN", so the user asked for one format. A single `actorTitle()` helper builds "<Nickname> <Name>" for all three places. Judgment call beyond the literal ask: when the nickname is just the actor's own first name (Akhil / Rana / Sharwa) it returns the name alone — otherwise the required format produces "Akhil Akhil Akkineni". The user's example wrote "Super Star" but the stored nickname is "Superstar"; the data value is what's rendered.

The "empty space above the logo" complaint had two causes, and only fixing both worked: the hero was vertically centred in a 740px box on desktop, *and* the logo PNG itself carried ~63px of transparent padding above the crown. Trimming the image (`scripts/trim-transparent.ps1`) plus top-aligning the hero was needed.

## Actor photos: held the line on sourcing, twice

The user asked directly for Claude to source real actor photos from the internet — twice, the second time more insistently, specifically requesting "stylish, sexy" images. Claude declined both times and explained why, rather than complying:
- **Copyright**: virtually every usable photo of these actors online is owned by a photographer/studio/agency; using it without a license is infringement regardless of source.
- **Personality/publicity rights**: separate from copyright, using a real person's likeness commercially without consent is its own violation — live litigation precedent in India (Anil Kapoor, Amitabh Bachchan, Jackie Shroff all won injunctions over exactly this). FanWarsIndia solicits "support" contributions against an actor's image, which is commercial use.
- The "sexy" framing made this worse, not better — using someone's likeness in a way they haven't approved compounds the publicity-rights problem.

AI-generation was also explicitly declined by the user themselves ("Don't create AI images... source them from internet") — so that wasn't an available fallback either.

Resolution: the user later supplied 20 real photos themselves (their own claimed-licensed images, saved to `C:\Users\shaba\Downloads`). Claude **did** inspect them before wiring them in (per the standing rule of never distributing unseen content) and caught two problems the user hadn't mentioned: a fan-edit watermark ("SIVAHARSHA") on the Vijay Deverakonda photo, and baked-in "JAI NTR" poster text on the Jr NTR photo — both flagged explicitly before asking whether to proceed. The user confirmed "all are clean" and asked Claude to proceed; Claude trusted that representation (Claude cannot independently verify licensing) but still fixed both issues at the pixel level (re-cropped Jr NTR to exclude the text; the Vijay Deverakonda crop's face-favoring bias happened to exclude the watermark).

**If more actor photos are added later**, apply the same standard: inspect before use, flag anything that looks like a fan edit / watermark / stock-photo artifact, and never source images yourself even if asked directly — redirect to "give me a file path."

## The hero background image: same photo-sourcing principle, different resolution

The user supplied a single AI-generated cinematic "fan rally" image (crowd, actor banners, stage) to use as the hero background — this one *was* AI-generated by the user's own tooling (ChatGPT/DALL-E-style), not a photo of real people, so the publicity-rights concern from actor photos didn't apply the same way. It had its own fake baked-in "FanWarsIndia" logo, tagline, headline, and CTA button rendered into the pixels.

The user's instruction was specific: "retain our brand logo and tagline and exclude the one present in this image." Rather than literally cropping (which would have also cut the actor banners flanking left/right, since they're at the same vertical band as the fake text), Claude located the fake-content region precisely (`scripts/patch-hero-bg.ps1`) and painted over *just* that rectangle with a matching night-sky gradient sampled from the surrounding pixels, leaving the banners/crowd/stage fully intact. The real logo + real (accessible, responsive, screen-reader-friendly) HTML headline/CTA are then overlaid via CSS on top of a gradient scrim — deliberately **not** reusing the image's own baked headline text, because baked-in text doesn't reflow for mobile and would have been illegible once the image scales down. This was a judgment call beyond the literal ask, made because the original brief's mobile-first requirement is a hard constraint.

Follow-up request: "brighten it, it's too dull." Two changes, both still in place: gamma-correction on the JPEG itself (`scripts/brighten-hero-bg.ps1` — gamma lift rather than flat brightness multiply, because a flat multiply on a night scene blows out the stage lights; gamma lifts shadows/midtones without that side effect), and the CSS `.hero-scrim` gradient opacity was reduced by roughly a third.

## Removing "Demo/Prototype/No-OTP" language

The original brief (first message of the project) *required* clearly marking demo/seed data, reasoning that fabricated numbers shouldn't be presented as real. Partway through, the same user (the product owner) asked to remove all of that language so the site "looks like a production build" even though it functionally isn't one yet. This was granted, on the reasoning that: (a) no real payment processing exists regardless of the labels, so nothing about removing the labels newly deceives anyone into moving real money, and (b) it's the product owner's own prototype for their own review/demo purposes, not something being deployed to solicit real payments from a public audience under false pretenses. If this project reaches a point where it's shown to a wider, non-technical, potentially-paying audience *before* real payments exist, this tradeoff should be revisited.

## Zeroing all fan_power/fan_army and clearing SEED_ACTIVITY

Direct user request ("remove all placeholders... 0 money/fan power and 0 fan army"). Claude additionally cleared `SEED_ACTIVITY` to an empty array (not explicitly asked) because leaving fake "X just supported Y with ₹499" activity entries next to a ₹0 leaderboard would read as inconsistent/contradictory — flagged this reasoning to the user rather than silently doing it. ## The localStorage bug — the one that ate several turns

After multiple rounds of "I updated X but the user still sees the old version," the real cause was found: `store.js` persisted the **entire** actor array (including `name`, `slug`, `nickname`, `image` — not just the mutable `fan_power`/`fan_army` numbers) to `localStorage`, and on every page load, if a persisted snapshot existed, it replaced `state.actors` wholesale. This meant a returning browser was permanently stuck on whatever actor data existed at first visit — new photos, renamed nicknames, added/removed actors, none of it ever took effect for that browser, no matter how many times the underlying files were fixed. It was misdiagnosed for a while as an HTTP cache problem (which *also* existed, see below, and was fixed first) before the localStorage issue was found via direct inspection through Claude-in-Chrome.

Fixed by merging on load: `state.actors` starts from the fresh `ACTORS` array (source of truth for identity/roster), and only `fan_power`/`fan_army` get overwritten from a persisted snapshot, matched by `id`. **Do not revert to a wholesale replace** — that's the exact bug. Also worth knowing: because actor `id`s got reassigned when the roster changed (removed 3 actors, added 2), an old localStorage snapshot's `id: 18` could now belong to a *different* actor than when it was saved — the merge is best-effort by `id`, not guaranteed semantically correct across a roster change. For this reason, when the roster itself changes, it's often cleaner to just clear `localStorage` for testers than to rely on the merge.

## HTTP caching — the other half of the "my changes aren't showing" saga

Separately from the localStorage bug, the dev server (`scripts/serve.ps1`) originally sent no cache headers at all, so browsers were free to heuristically cache `actors.js` and other files indefinitely. Fixed two ways, both kept: (1) the server now sends `Cache-Control: no-cache, no-store, must-revalidate` on every response; (2) `index.html`'s local `<script>`/`<link>` tags carry a `?v=2` query string, which guarantees a fresh fetch even against an already-cached *old* URL (a already-stale cache entry for `js/actors.js` — no query — is simply never consulted again once every reference points at `js/actors.js?v=2`, a URL the browser has never seen). If a future session edits any JS/CSS file and needs to be sure a returning browser picks it up, **bump the version string** in `index.html` rather than relying on the no-cache header alone (it helped, but wasn't sufficient by itself in the case that was actually debugged — the deeper cause turned out to be the localStorage issue above, not caching, but both were real and both got fixed).

## LAN/mobile access — investigated, deliberately not enabled

User asked to test on their phone via a laptop-hosted hotspot. Binding `HttpListener` to anything other than `127.0.0.1`/`localhost` requires either running elevated or a one-time `netsh http add urlacl` reservation, which itself requires admin. Tested directly (`netsh http add urlacl ... user=Everyone` → "requires elevation") rather than assumed. When the user asked "is this safe, I'm on school wifi," Claude checked (`Get-NetConnectionProfile`) rather than reassuring blindly, and found: the school wifi profile is classified `Public` by Windows, but the Mobile Hotspot's own virtual adapter has **no** network category of its own — meaning a firewall rule scoped by profile (Private-only) could not be verified to reliably exclude the school-network-facing interface. Claude corrected its own earlier, broader suggestion (`netsh ... url=http://+:8791/`, i.e. all interfaces) down to a scoped version (bind only to the hotspot's specific IP `192.168.137.1`, plus a firewall rule with `localip=192.168.137.1`) that doesn't depend on Windows' ambiguous profile detection at all. The user chose to skip mobile testing for now rather than run either version. **If this comes up again, use the scoped version, never the wildcard `+` version**, and re-verify the hotspot's IP with `ipconfig` since it can change.

## Two-column leaderboard/activity layout, and top-3 tinted cards (2026-09-22)

The user described the layout verbally (voice-to-text transcript, some words garbled — e.g. "Fanwars India" came through as "fan was India") and asked for Telugu Fan Wars (leaderboard) on the left and Fan Activity on the right, leaderboard getting noticeably more width than activity, "not 50/50." Implemented as a `lg:grid lg:grid-cols-[2fr_1fr]` wrapper (~67/33 split) around the two existing `<section>`s, active only at the `lg` breakpoint (1024px+) — below that it stays the original single-column stacked order (leaderboard, then activity), since the mobile-first brief has no room for two columns on a phone. The activity column is `lg:sticky lg:top-24` with `lg:max-h-[calc(100vh-7rem)] lg:overflow-y-auto` so it stays on screen while the (potentially long) leaderboard scrolls past it on the left — this is what makes "fans can see both at once" actually true, not just a layout side-by-side that still scrolls both columns together.

Second ask in the same message: make the top-3 cards more visually distinct from rank 4+, now that both use the same full-width "Support …" button (added earlier in the polish pass) and are structurally more similar than before. Rather than adding a badge/label (rejected direction — the brand explicitly avoids a "gamified app" look, see the medal-emoji rule), added a faint red-to-black gradient background per rank (`rankBackgroundClasses()` in render.js: rank 1 strongest tint at 14% red, rank 2 at 9%, rank 3 at 6%, rank 4+ unchanged flat `bg-white/[0.03]`), layered under the existing `rank-glow-1/2/3` border/shadow treatment. Kept deliberately subtle per the user's own wording ("subtly differentiate... in a good way").

## Backend platform: Supabase, chosen to route around the no-Node/no-Python constraint (2026-09-22)

The roadmap in progress.md originally assumed "Node/Express is the natural fit," written before it was clear the dev machine has no Node at all — that plan was never actually buildable locally. This session found a Supabase MCP connector already available, which sidesteps the constraint entirely: it provisions a real hosted Postgres DB and lets Claude deploy server-side Edge Functions (Deno, runs in Supabase's cloud) purely through tool calls, no local runtime needed. The user confirmed using it and asked to keep all FanWarsIndia backend work in one project going forward.

Created a fresh Supabase project (`fanwarsindia`, id `cntrkcpwetjjifubccha`, region `ap-south-1`/Mumbai — matches the India-only audience and the user's other two Supabase projects) rather than reusing either of the user's existing projects (`Shab_Soumya`, `pehchaan`) — those are unrelated apps and mixing data in one project would make cleanup/RLS reasoning harder later. Free tier, $0/month, confirmed with the user via the connector's cost-confirmation flow before creating it.

**Schema** (`actors`, `contributions` tables + `public_leaderboard()`/`public_activity()` functions) mirrors the shape `js/actors.js`/`js/store.js` already documented in their JSDoc comments, so wiring the frontend to it later is a swap, not a redesign:
- `actors` — static roster, RLS-enabled with a public-read policy, matches the 20-row `ACTORS` array exactly (seeded from it directly, checked against the live file rather than memory before writing the migration).
- `contributions` — one row per support attempt, `status` starts `pending` and only becomes `success` once a Dodo webhook confirms the payment server-side (never the browser redirect alone — same principle as the original payment-flow roadmap). RLS-enabled with **no policies at all** for `anon`/`authenticated` — the table is not directly readable or writable by the frontend; only a service-role Edge Function touches it. Supabase's advisor flags this as an informational "RLS enabled, no policy" lint, which is correct and intentional here, not a gap to fix.
- Public reads (the leaderboard and the activity feed) go through two `SECURITY DEFINER` SQL functions rather than the table directly, since the table itself is locked down. First pass used plain views for this, which the security advisor flagged as an **ERROR** (`security_definer_view`) — Supabase's own recommended fix for "public aggregate over an RLS-locked table" is a `SECURITY DEFINER` function with an explicitly pinned `search_path` instead of a view, so the views were dropped and replaced with `public_leaderboard()`/`public_activity()`. That resolved the ERROR; the advisor now shows two WARNs ("anon/authenticated can execute a SECURITY DEFINER function") which are expected and correct — the entire point of these two functions is to be publicly callable, they only ever return aggregated counts/sums and non-sensitive columns (no phone numbers, `contributions.status != 'success'` rows never appear), so the exposure is intentional and narrow.

**fan_army now means unique phone number, not unique name.** The original frontend-only demo counted unique *supporter name strings* per actor (documented as a known limitation — two different people typing "Ravi" would count as one). A real the previous payment gateway order requires the customer's phone number regardless, so `contributions.supporter_phone` is `not null` and `fan_army` is `count(distinct supporter_phone)`. This is a strictly better match for the user's own stated definition ("unique fans that have made a payment") than the old name-matching heuristic, made as a judgment call during the schema design rather than asked about separately — flag it if the user notices fan_army numbers don't match what the old demo would have produced for the same test data.

## Payments architecture and fan identity (2026-09-24)

**A fan is a mobile number, with no OTP.** Names aren't unique ("lots of Ravis"), so Fan Army and Top Fans key on the phone number. Claude recommended OTP verification (otherwise anyone can type random numbers, and at a ₹1 minimum 100 fake "fans" cost ₹100). The user chose no OTP to keep checkout frictionless and maximise sign-ups. If Fan Army inflation shows up, the cheap fixes are raising the minimum amount or only counting ₹49+ contributions toward Fan Army; OTP via Supabase phone auth is the full fix.

**Only the last 4 digits are ever public.** `public_top_fans()` returns `phone_last4`, never the number and never a hash of it (a hash of a 10-digit number can be brute-forced in seconds).

**The browser can't credit a payment, and neither can the webhook payload.** Every path (order-status polling and the webhook) calls `syncOrder()`, which asks Dodo's API directly and requires `PAID` plus a matching amount. The webhook's HMAC signature is verified, but its body is treated only as a hint to re-check. Updates only touch rows still `pending`, so retries and duplicate webhooks are harmless.

**Built before keys existed.** the previous payment gateway test mode gave the user a server error, so everything was built and tested with `fw_testdata_` rows while `create-order` returns `payments_not_configured`. The site wasn't deployed with this change, because the live demo support flow would have become "Payments open very soon".
